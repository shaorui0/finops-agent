储蓄核实：resolved 的 finding 真的省钱了吗

本页由 python3 -m finops_agent.verify_savings 生成，所有数字来自代码。

1 问题与口径

agent 把一条 finding 标成 resolved，只说明这个 key 在本次巡检里不再出现。它不说明账单降了，也不说明降了多少。finding 里的 monthly_savings_usd 是提出时的估算。本文用每个周期自己的 Cost Explorer 数据核实：被处理的资源在下一个周期到底少花了多少钱，和当初预测的差多少，差在哪，钱有没有留住。

结论先行：三个周期（2026-09、2026-10、2026-11）里共有 4 条 resolved finding，预测合计 $89.60/月，经对照组校正后实现 $89.60/月，实现率 100.0%。4 条实现率在 ±2% 内。其中 1 条在下一个周期丢失（F06 gp2 改 gp3，每月 $20.00）。

口径

  • 预测：finding 的 monthly_savings_usd。basis 有三类：list_price（牌价估算，按 30 天标准月），billed 与 billed_14d_extrapolated（账单实际，agent 把近 14 天外推到分析周期的天数），inferred（推断）。
  • 标准月：30 天。测试世界的每条成本行都是月价除以 30，所以用 30 天作单位；账单外推型预测先乘 30 除以 N 期天数，换到同一单位再比较。真实账号应换成 730 小时。
  • 实现节省：被处理资源在 N+1 期的反事实成本减实际成本。反事实 = N 期日均成本乘对照组漂移系数 g。对被删除的资源，实际成本取期末的稳态日均成本（期中删除的，删除后为 0）。
  • 实现率：实现节省除以预测（均为标准月美元）。±2% 内算兑现，高于 102% 算超额，2% 以下算未兑现，其间算部分兑现。
  • 保持：同一条 finding 在 N+2 期再测一次（反事实仍用 N 期日均成本和 N 到 N+2 的对照组漂移）。N+2 实现为 0 则记为兑现后丢失。
  • 首月现金：N+1 期反事实成本（按 N+1 的真实天数）减实际成本。它回答财务月报上会看到多少，和标准月口径的差别单列为偏差原因。
  • 金额口径：成本一律取 UnblendedCost（账单实际）。AmortizedCost 只用来检测承诺吸收。

2 数据

每个周期起一套 test-aws-server 和 test-metrics-server（端口 34566 起，周期之间先关再开），用 --world 选当期世界：基础世界、testenv/scenarios/next_month.yaml、testenv/scenarios/month_after.yaml。agent 用 --no-judge 跑三次，共用一个 state 文件，写法与 scripts/rot_demo.sh 相同。agent 之外，用 boto3（endpoint_url 指向测试服务器）直接查该周期的 Cost Explorer：

  • 资源级：GetCostAndUsageWithResources，日粒度，按 RESOURCE_ID 和 USAGE_TYPE 分组，UnblendedCost 与 AmortizedCost。接口限制单次不超过 14 天，所以每个周期分段查询再相加；接口要求带 Filter，取该周期出现过的全部 SERVICE。

3 方法（含反事实基线与混杂因素）

账单差 = 节省 + 一切别的变化。要证明钱是省下来的，必须把别的变化挪出去。方法分五步，全部由 finops_agent/verify_savings.py 的确定性代码完成，没有 LLM 参与。

  • 第 1 步，配对：N+1 期 diff 的 resolved 列表里每个 key，回到 N 期的 findings 找到同 key 的 finding，取它的预测、basis 和资源列表。资源 ID 在账单里没有行的（例如 AMI），记为未对上，只核实有行的部分。
  • 第 2 步，基线：N 期被处理资源的日均成本 = 资源级成本 / 该资源有账单的天数。中途创建的资源按有账单的天数算，所以半个月的资源不会被低估。
  • 第 3 步，对照组：资源级成本在 N 与 N+1 都出现、N+1 期末仍在计费、且不属于任何 resolved / regressed / new finding 的资源。按用量类型类别分层（ebs_volume、ebs_snapshot、public_ipv4、compute、nat，其余各自一层）。漂移系数 g = 层内对照资源 N+1 日均成本之和 / N 日均成本之和。某层没有对照资源，就用全体对照资源的 g，并在表里标出。
  • 第 4 步，反事实与实现：反事实日均成本 = N 日均成本 x g。实现节省 = (反事实 - N+1 稳态日均成本) x 30。同时给出不校正的朴素值（N 减 N+1），两者之差就是校正量。
  • 第 5 步，偏差分类：对每条核实按规则打标。日历月天数（N+1 不是 30 天）；按天折算（资源在 N 或 N+1 只计费一部分天数）；对照组校正（校正量超过预测的 2%）；预测口径（牌价与账单是否一致，外推是否与 N 期成本一致）；承诺吸收（摊销口径节省比账单口径多出 2% 以上，说明差额进了 Savings Plan 未用承诺）。

  • 实现率 100.0% 是这个测试世界里的零结果，不是方法的功劳：世界用同一张价格表生成预测所依据的成本行和账单，预测本来就应该对上。这里的证据价值在三处：流水线（采集、汇总、折算、配对）没有凭空制造偏差；两张发票之差（$83.73）、首月现金（$92.05）与标准月实现（$89.60）的差别被逐项解释；方法在能制造偏差的合成案例里给出了正确的偏差。

7 局限

  • 数据是合成的。世界文件同时生成成本行和价格表，所以表 13 的对账证明的是汇总与折算逻辑没错，不证明真实账单的行为：折扣、积分、退款、预留实例、跨月结算调整在这里都没有。方法里为承诺吸收留了检测，但三个场景里没有被承诺覆盖的 resolved 项，该检测只被单元测试覆盖，没有被真实场景验证。
  • 场景里的删除都发生在周期开始之前（覆盖层一次性移除资源，成本行整月消失）。中途删除的折算由单元测试覆盖，场景数据里没有一个中途删除的样例；需要这类样例时要在 testenv 里给资源加删除日期，不在本 change 的范围内。
  • 对照组的假设是同层资源的用量按同一比例漂移。核实所用的层及其对照资源数：ebs_volume 层 1 个（g=1.0000）；public_ipv4 层 1 个（g=1.0000）。同层对照很少，且被处理资源所在层的 g 全部为 1，校正量为 0。单元测试验证了校正公式，真实场景没有给出非平凡的校正，所以『校正有效』这一条的证据来自合成案例，不来自场景。
  • resolved 只核实了 findings 里 monthly_savings_usd 大于 0 的项。savings_plan_underutilized 的预测为 0，持续 persisting，没有进入核实。三条没被 --no-judge 跑出的判断层 finding（ingest 车队、NAT、跨 AZ）不在本文范围。
  • 标准月取 30 天是测试世界的定价约定。真实账号按小时计费，应使用 730 小时。资源级成本在真实 AWS 里只对 EC2 相关服务提供且最多回溯 14 天，对更早周期要靠自己保存的数据，不能事后补查。
  • 只有 3 个周期。保持只测了一期（N+2）。节省是否能保持半年，这里没有证据。

8 结论

  • resolved 与账单一致：4 条 resolved 的资源在下一期账单里都真的少了成本，预测合计 $89.60，标准月实现合计 $89.60，实现率 100.0%。逐条实现率均落在 ±2% 内的有 4 条。
  • 预测与实现的差别来自口径，不来自错误：账单外推型预测带着 N 期的日历天数（2026-09 30 天、2026-10 31 天、2026-11 30 天），换算到标准月后与实现一致；牌价型预测（gp2 改 gp3）与账单实测一致。逐条实现率都在 ±2% 内，没有发现预测的系统性高估或低估。
  • 一次兑现不等于留住：F06 在下一期被回退，$20.00/月 的实现归零。resolved 之后要持续看 regressed，这条已有告警 FinOpsRegression。
  • 账单分解精确闭合：2026-09 到 2026-10 账单差 +$474.93，其中已核实节省 $76.05；2026-10 到 2026-11 账单差 -$285.65，其中已核实节省 $16.00。账单涨跌与节省没有直接关系。
  • 方法没有被真实世界的折扣、承诺覆盖、中途删除考验过，这三项只有单元测试覆盖，见第 7 节。下一步需要给场景加中途删除和承诺覆盖的 resolved 样例。
