c0018-savings-verification：用账单核实 resolved 的 finding

改了什么、为什么：见下。完整数据、方法、逐条核实表与账单分解在 储蓄核实文档（由代码生成）。

为什么

rot 检测（c0010）把 finding 标成 resolved，但 resolved 只说明 key 不再出现，不说明账单少了钱。finding 里的 monthly_savings_usd 是估算。没有对账，「清理见效」只是叙述。维护者的要求：实验数据、为什么对、怎么验证真的省钱了、数据分析结论，要有细节。

改了什么

  • 新增 finops_agent/verify_savings.py：对三个周期（2026-09 基础世界、next_month.yaml、month_after.yaml）各跑一次 agent（--no-judge，共用 state），再用 boto3 查每个周期自己的 Cost Explorer（资源级日度 + 用量类型级月度）。对每条 resolved finding 计算预测、反事实基线、实现节省、实现率、偏差分类、下一期是否保持，并把整张账单的变动精确分解。
  • 新增 docs/SAVINGS_VERIFICATION.md（中文，所有数字由代码生成）与 reports/savings-verification.html。
  • 新增 scripts/verify_savings.sh（端口 34566 起）与 finops_agent/test_verify_savings.py。

关键结果

  • 4 条 resolved，预测合计 $89.60/月，标准月实现 $89.60/月；逐条 100.0%。
  • gp2 改 gp3：10 月兑现 $20.00，11 月被 terraform 回退归零（兑现后丢失）。
  • 10 月账单涨 $474.93，同期已核实节省 $76.05：日历天数 +$290.43，用量漂移 +$247.75，新增浪费 +$12.80。分解与实际账单差精确相等。
  • 分层对照组：全体 g=1.028，EBS 层 g=1.000，不分层会多算 2.8%。

设计

比什么

预测 = N 期 finding 的 monthly_savings_usd。实现 = 被处理资源在 N+1 期的反事实成本减实际成本。实现率 = 实现 / 预测。

关键决定

  1. 反事实，不是两张发票相减。 发票差混进日历天数（10 月 31 天）、用量漂移（NAT 字节）、中途创建的资源、新增浪费。反事实 = N 期日均成本 x 对照组漂移 g。对照组 = 两期都在计费、期末仍在、且不属于任何 resolved / regressed / new finding 的资源。
  2. 对照组按用量类型类别分层。 实测：全体对照的 g 是 1.028（被 NAT 拉高），而 EBS 层 g 是 1.000。不分层会把卷的节省凭空多算 2.8%。某层没有对照资源才退回全体，并在自检清单里标出。
  3. 标准月 30 天。 测试世界所有成本行是月价 / 30。billed 型预测被 agent 外推到 N 期天数（analyze.py：cost * days / res_days），先乘 30 / N 期天数再比较。list_price 型本来就是 30 天。真实账号应换 730 小时。
  4. 日均成本，不是发票成本。 中途创建的资源（restore-scratch 卷 10-08 创建，10 月只计费 24/31 天）用有账单的天数算日均；期中删除的资源，稳态取期末是否仍在计费。
  5. 同时算 Unblended 与 Amortized。 摊销口径节省大于账单口径时标「承诺吸收」：被 Savings Plan 覆盖的实例停机，账单不动，节省进了未用承诺。
  6. 保持测量。 同一条 finding 在 N+2 期再测一次。gp2 改 gp3 在 10 月兑现，11 月被 terraform 回退，必须显示「兑现后丢失」。
  7. 账单分解精确闭合。 逐资源键的恒等式 c1 - c0 = (c1 - cf) + (cf - c0)，cf - c0 = (rate0 x d1 - c0) + rate0 x (g - 1) x d1，加总成七项：已核实节省、回归损失、新增浪费、日历天数、用量漂移、其他移除、其他新增。全程 Fraction 运算，等式精确成立，不是舍入后相等。
  8. 独立复算。 用世界价格表（单价 x 规格）重算被处理资源的标准月成本，与 Cost Explorer 汇总比对。

范围之外

场景里没有中途删除、没有被承诺覆盖的 resolved 项；这两个检测只由合成单元测试覆盖。给场景加这类样例需要改 testenv，不属于本 change，记入证据的 NEXT。

笔记

  • resolved 不等于省钱。agent 只知道 key 不见了。要证明省钱，得拿下一期的账单去对：被处理资源的反事实成本减实际成本。
  • 两张发票相减是错的方法。10 月到 11 月的真实演示里：三项清理省 $76.05，账单却涨了 $474.93，因为 10 月多一天（+$290.43）和 NAT 用量上涨（+$247.75）。只看总账单会得出「清理没效果」。
  • 对照组必须分层。全体对照的漂移系数是 1.028，被 NAT 拉高；卷所在的 EBS 层是 1.000。不分层会把卷的节省多算 2.8%。
  • agent 的 billed 型预测是按分析周期的天数外推的（analyze.py 里 cost * days / res_days）：10 月的预测是 16.53，30 天的实现是 16.00。这不是错误，是口径。先把预测换到标准月再比，实现率才是 100%。
  • 实现率 100% 是零结果，不是方法的功劳：世界用同一张价格表生成账单和预测依据。证据价值在于流水线没凭空制造偏差，以及方法在合成案例里能给出正确的偏差（用量降、涨、中途创建、承诺吸收）。
  • gp2 改 gp3 在 10 月完全兑现（实现 $20.00），11 月被 terraform 回退归零。一次 resolved 不是终点，要在 N+2 期再测一次。
  • 账单分解用 Fraction，等式 sum == delta 精确成立。浮点下只能 assertAlmostEqual，不能证明没有漏项。
  • 踩坑一：resolved 列表来自集合差，顺序随哈希种子变，文档两次生成不一致。确定性测试（采集两次比对）抓到的，修法是按 key 排序。
  • 踩坑二：boto3 的 get_cost_and_usage_with_resources 要求必带 Filter（真实 API 也如此），资源级请求还限 14 天，要分段。
  • 场景里没有中途删除、没有承诺覆盖的 resolved 项，这两个检测只有合成单测。要补样例需要改 testenv，这个 change 不能碰。
