c0020 ring 1 稳定化

改了什么：ring 1 只用文字说需要什么信号（signal / concept / terms / scope），不写指标名；ring 2 按含义在在线服务器的指标目录（名字、HELP、scope 标签）里确定性地发现候选名；ring 4 可按 need 级给出 SLI 的 covered/partial/missing 混合状态；评估加 --samples N。

为什么：c0017 重采样 overlap 为 0.91、0.82、0.64（均值约 0.79），根因是猜出不存在的指标名，以及合并 SLI 里一个 need 缺就整个 missing。

结果：N=5 overlap 均值 0.964（min 0.91，max 1.00），评审路径不变。详细证据如下。

读法： 1. 评审版 ring 4：4 covered / 2 partial / 2 missing。派生版（mix 模式）：3 covered / 5 partial / 0 missing。c0017 里同样的派生版是 2 covered / 0 partial / 5 missing。合并 SLI 里有一个 need 没找到，不再让整个 SLI 变 missing。 2. 派生版没有 missing，不等于比评审版好：partial 里的 need 级 partial（例如 0/2/1）是指标找到了，但 scope 没覆盖全（service 列表里有的服务没有这个指标），这是真实的覆盖缺口。 3. 评审版里 planted gap 的内存和「处理字节数」，ring 2 都没有候选（(no candidate)），ring 3 照实记 missing，没有被 CPU 指标或 db_client_bytes_total 顶替（泛词规则挡掉了这类误配）。 4. ring 2 的发现不完美：「successful requests or jobs completed」没有候选；「completed ingest jobs count」把 ingest_job_retries_total、ingest_downstream_errors_total 也带进来了。候选宁多勿漏，之后由 ring 3/4 检查。 5. 评审版 rightsizing_headroom 在 ring 4 是 missing，是因为内存本来就没有（planted gap），不是派生版的问题。

6 局限与事故

  • 均值达标是「ring 1 说词 + 一个确定性 discover」合起来的结果。discover 的规则（至少 2 个 term、泛词不能单独撑、scope 标签、3 个字符以上做子串匹配）是看过测试服务器目录之后定的，换一个命名风格不同的服务器，召回可能下降。这个 overlap 不能外推到真实环境。
  • GENERIC 泛词表和子串规则是代码里的词表，不在 prompt 里，不违反 FA12，但它是调参点。
  • precision 0.78 到 0.93（5 次均值 0.857）：LLM 多写的 need 有些在服务器上没有对应指标（磁盘 IO 等），属于「我需要但看不到」，不算错。
  • 评审版只有 11 个 need，漏 1 个就是 0.09，所以 min 0.91 对应漏 1 个。
  • 事故：写本文件时 shell 误把 Markdown 里的反引号 make eval 当命令执行了一次，在默认端口 4566/9090 起过测试服务器，跑完由 make stop 关掉，之后确认没有监听残留。其余所有运行都用 36566-36571。
