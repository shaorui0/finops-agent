# 构建过程：这个项目怎么用 agent 做出来

代码和文档只是结果。这份文档讲过程：单个改动怎么走闭环，24 个 agent 怎么分四波并行做完同一份完成标准，以及过程中出过的事故和它们教会我的东西。完成标准的逐条状态见 [`MATURITY.md`](MATURITY.md)。

## 单个改动的闭环

每个改动是一个 OpenSpec change，规则全文在 [`../CONTRIBUTING.md`](../CONTRIBUTING.md) 和 [`.claude/skills/finops-change-loop/SKILL.md`](../.claude/skills/finops-change-loop/SKILL.md)。

![Harness 分层](diagrams/harness-layers.svg)

1. 开 change，写 proposal、specs、tasks，tasks 里必须有一条验收，写明用什么命令证明做完。
2. 实现，只改 tasks 里列出的东西。
3. 验收，输出原样存进 `evidence.md`，失败回到实现。
4. 出一份 HTML 报告和一份原始笔记（只记想法、坑和反直觉的结论，不润色）。
5. 按阶段提交（proposal、spec+tasks、impl、docs、acceptance），每次只 `git add` 该阶段的文件。
6. 把验收结果汇报给维护者，没汇报不算做完。

笔记最后一行固定是 `PROGRESS_ROW:`，README 进度表的行就从这里取，所以进度表不靠记忆。

## 多 agent 调度

c0009 之后的 24 个 change 不是我一个会话串行做的，而是按一份预先批准的完成标准并行推进。规则如下。

| 规则 | 做法 | 为什么 |
|---|---|---|
| 完成标准是唯一停机判据 | 20 条 D 项，每条写明验证命令；全部勾完才停 | agent 自己说「做完了」不算，判据可复现才算 |
| 每个 agent 一个 worktree | 独立 git worktree 和分支，端口段各不相同 | 并行改同一个仓库不会互相覆盖，也不会抢服务端口 |
| 声明 owned_paths | 每个任务写明可以改哪些路径，越界要在回报里写理由 | 合并冲突在派活时就被规避；越界是信号，不是默认 |
| 主 agent 只合并并重新验证 | 不改业务文件；合并后在主干上重跑 `make test`、`make eval` 和带私有词表的 `make check` | 子 agent 的自述只是线索，主干上的重跑才是证据 |
| 变更走 escrow | push、改全局设置这类对外或不可逆的动作，agent 只登记命令和验证方式，由人批准后再执行 | 把「能做」和「该不该做」分开，批准过的才执行，执行后还要验证 |
| 下一波准入规则 | 子 agent 回报的 NEXT 必须指向一条未勾的 D 项，或推翻一个既有事实，才进入下一波；否则记入延后清单 | 防止每一波都长出新活，停机判据才有意义 |
| 上限 | 4 波，24 个 agent，用满即停 | 到上限时剩下的由主 agent 只读复核和维护者阅读 |
| 回报格式 | 做了什么、证据、命中哪条 D、阻塞、NEXT 指向哪条 D、待执行的变更 | 每条带出处和置信，主 agent 可以逐条核对 |

## 事故与教训

下面每一条都是真实发生、被记进调度记录的。

### 泄漏扫描在合并之后才拦下

c0009 的 evidence 里有一行本机绝对路径。子 agent 先跑检查、后写证据，而且 worktree 里没有私有词表（`.leak_patterns.local` 被 gitignore，不会跟着 worktree 走），所以它的检查只扫公开模式。合并后主 agent 带着私有词表重跑，才被拦下。

教训：检查要在证据写完之后跑；私有词表要复制进每个 worktree（本 change 的第一步就是复制它）；主 agent 合并前必须用带私有词表的检查复核。

### 合并两条分支后测试的全局状态泄漏

合并后 `make test` 出现 1 个失败和 1 个错误：一个场景一致性测试的 setUpClass 报错后，世界选择没有恢复，后面的测试读到了场景世界。单独跑每个测试都通过，合并后一起跑才暴露。修法是在测试里关掉 judge 并在 cleanup 里恢复世界。

教训：每条分支单独绿，不代表合并后绿；全局状态（当前选择的世界）必须在 cleanup 里还原；合并后整套重跑是必需的，不是形式。

### 导读页每次合并都会过期

导读页由 `tools/build_index.py` 从仓库状态生成，列出每个 change。新 change 合入后，`tools/test_build_index.py` 立刻失败，因为新 change 没被列入。这是预期内的失败，但每一波都要重建一次导读页，并登记为「生成而不是手改」的白名单例外。

教训：生成物的新鲜度要由测试守住，失败本身是信号；重建是机械动作，不该靠人记得。

### 诚实的自述让判据变严，而不是让勾变多

- t8 回报 LLM 推导第 ① 环单次录制 0.91，但重采样 0.82、0.64。主 agent 没有勾 D7，把判据收紧成不少于 5 次采样的均值，再派一个任务去稳定它。
- t16 回报核实的 4 条全部 100%，并指出这是零假设结果（账单和预测同源于价格表）。主 agent 没有勾 D19，把判据收紧成「至少一条实现率不为 100% 且原因被正确归类」，派 t18 喂真实偏差。
- t2 回报 9 个对抗变体里有 1 个压掉了真实 finding。D3 没勾，派 t19 修校验器。

教训：agent 愿意如实报告「我的结果不够强」，调度规则就要奖励这一点：不满足就收紧判据并派下一个任务，而不是勾上它。

### 一次修复推翻了既有语义

t2 的样本外评估发现：带跨周期状态跑时，漏检的 finding 会被记成 `resolved`，漏检伪装成整改。这推翻了「resolved 等于已整改」这个既有事实，按准入规则可以进入下一波。结果是 `not_redetected` 状态和持续异常线索（c0023）。

教训：评估不只量 agent，也会暴露周边语义的错误，这类发现的价值高于再涨一点指标。

### 预注册

c0023 对着样本外失败修完之后，那两个世界不再是样本外，没有一个未被污染的数字了。维护者同意再加一个全新的世界，于是有了 c0024：标准答案和评估规则先提交，之后才第一次运行，只评估一次，agent 不改。结果 recall 0.75，比样本内的 1.0 低（详见 [`../eval/EXPERIMENTS.md`](../eval/EXPERIMENTS.md) §7）。

教训：「样本外」是一个流程属性，不是数据属性；冻结在前、结果原样报告，按预注册的规则不据此改代码，三个漏检因此留成已知缺口，而不是被悄悄修掉。

### 其他小坑

- 某个 agent 的未加引号 heredoc 误在默认端口上跑了一次 `make eval`，已退出，无残留。之后每个任务用自己的端口段。
- 一个任务的 acceptance 提交标成 `[5/5]`，实际只有 4 个阶段，历史保留没有改写。
- 测试里查「诱饵数字不在 `findings.json`」时，子串匹配误中了另一个数字里的片段，要按整数边界匹配。

## 没有的东西

- 调度器本身（派活、等回报、合并）是仓库外的 harness，本仓库只留下过程的结果和这份记录。
- 没有真实 AWS 账号上的运行。
- 事故里的两个（泄漏、全局状态）都是合并之后才发现的，说明合并前的验证有缺口，补救是事后的。
