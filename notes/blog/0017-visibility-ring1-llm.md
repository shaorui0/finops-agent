# 0017 让 LLM 推可见性链第 ① 环

- 第 ① 环的价值在「先不看系统」。让 LLM 只读业务语言的目标文件、不给任何指标名，它能推出 8 个 SLI，评审版 11 条需求覆盖到 10 条（0.91）。但这是挑出来的一次采样：同一 prompt 重采样是 0.82、0.64，均值约 0.79。单次达标不算稳定达标。
- 反直觉：overlap 0.91，ring 4 缺口表却从 4/2/2（covered/partial/missing）变成 2/0/5。名字覆盖得上，不等于缺口表等价。SLI 合并得粗，一个 need 找不到整个 SLI 就 missing；LLM 凭惯例写的名字（`aws_ec2_network_in.*`）服务器上没有，被记成缺口，但那是名字猜错，不是数据缺失。
- 所以第 ① 环由 LLM 写时，name 正则只该当「第一猜」；第 ② 环的计划应该按信号语义去服务器上发现名字，不能把 ① 的正则当事实。这是下一步。
- 它也有真用处：评审版里故意留的缺口（内存、job 处理量）它都独立推出来了，说明「要看什么」这件事 LLM 能做，「它叫什么」才是弱项。
- 坑：prompt 迭代最多 3 轮，第 2 轮我往 prompt 里写了 `_bytes_sum`、`_seconds` 当后缀示例，那是看过服务器指标名才想到的，等于泄漏。第 3 轮去掉后得分反而更高，说明泄漏没带来好处，但这一轮改动本身也是对着评审版的 miss 调出来的，有过拟合成分。
- 坑：匹配规则决定结论。服务器没有内存指标，评审版的 `.*mem.*` 在真实指标上命中为空，没法比；只好加了几个探针名，这是人为设定，写在 score_visibility.py 文件头。通配正则（命中超过一半）不计，否则 `.*` 就能拿满分。
- 坑：LLM 把 scope 当语义用。给 CPU 写 `services:web,api`，但 ring 3 的 `services:` 去查 `job` 标签，CPU 指标没有这个标签。第 2 轮在 prompt 里讲清 scope 的含义后才好转。
- prompt 卫生测试用真实服务器指标名和评审文件里的标识符片段断言：不在 prompt、也不在目标文件里。
- 7 次调用，约 0.215 USD。
