- 100% 的验证结果最不值钱。c0018 里预测和账单出自同一张价格表，对上是必然的；它只能证明流水线没有凭空造偏差，证明不了遇到偏差会分对类。要证明方法，得先造出真的偏差，再看分类对不对。
- 偏差要有出处。四个偏差都是世界文件里一处可指认的改动（删除日、SP 覆盖、增长、IOPS 与吞吐），核实器给的分类和改动一一对应。更硬的一条：不看任何账单，只从世界规格和价格表算出每项应有的节省，和核实器对账，1 美分内。这比「预测和账单对得上」强。
- 期中删除的首月现金实现率是 21/31 = 67.7%，不是预测错。发票、首月现金、标准月稳态是同一件事的三个口径，月报上看到的只是第一个月。
- dev 启停是承诺吸收的教科书：BoxUsage 与 SavingsPlanNegation 相抵为 0，承诺费固定，停机让承诺行的摊销同额变大（实例行少 $418.04，承诺行多 $418.04），两张账单合计纹丝不动。按需价算出来的 $580.61 一分钱都没省。
- 朴素对比能得出相反的结论：改 gp3 的同时数据涨 30%，两张发票差 -$8.00（改了反而更贵），对照组校正后实际省 $52.00。
- 对照组分层踩了个坑：闲置卷成本是平的，数据卷在涨，放进同一层，增长会被套到被删的闲置卷上，把 $60 的节省算成 $78。加一维「浪费类还是在用」，细层没有对照资源再退回粗类别，原链数字一个字都没变。
- 牌价预测在 31 天的月份偏大 31/30：agent 的 gp2 改 gp3 估算是 14 天账单外推到 N 期天数再乘 20%。9 月 30 天看不出来，10 月的 $62.00 暴露了，换算标准月 $60.00。
- gp2 改 gp3 对大卷不是净省 20%：gp2 给 3 IOPS/GB，3000 GB 就是 9000 IOPS，gp3 只含 3000，保留性能要另付 $35，预测 $60 实际省 $25。短缺与新增的两个用量类型恰好相等。
- C01 不是 agent 的输出。`--no-judge` 没有排期类检测器，判断层对 GT05 的结论本来就是「不要停」。核实「照按需价纸面值去停」会怎样，只能由场景声明这个纸面值，并在表里标来源 claim，组合里单列仅 agent 的实现率 85.9%。
- 踩坑：shell 的非引号 heredoc 里写 Python，字符串里的反引号会被 shell 当命令执行，一次误跑了 make test 和整条核实脚本，还把文档里的文件名吃掉。写带反引号的文本一律用带引号的 heredoc 或先写文件。
- 新增的世界字段必须用 sha256 证明不改变基础世界输出。vols 的 repr 因键顺序差点对不上，改成原顺序再比。
- 局限：仍是合成数据；对照组与被处理卷增速相同是场景设计的；diff_state 的 resolved 是「未再检出」，本链每个 resolved 都是资源真的变了，所以不受 t20 改语义影响。
