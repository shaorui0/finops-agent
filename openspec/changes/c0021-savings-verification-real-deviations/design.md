## 问题

c0018 的 100% 是零假设结果。要让核实器的每个分支都被真实数据考验，场景必须让预测和账单真的分开，并且分开的原因能从世界文件里指认。

## 关键决定

1. **新链，不改旧链。** 其他测试钉住 `next_month.yaml`、`month_after.yaml`、`adversarial_*`。新链 `verify_base -> verify_month1 -> verify_month2` 是基础世界上的覆盖层，旧链原样保留，在文档里作「零假设对照」。
2. **偏差由世界特性造成，不由代码里的补丁造成。** 三个可选字段：`deleted`（卷在该日之前计费）、`uptime: {fraction, since}`（实例按比例开机，BoxUsage 与 SavingsPlanNegation 同比例缩小）、gp3 `iops`/`throughput`（超出 3000 IOPS 与 125 MB/s 的部分按 `prices.gp3_*` 另计）。字段缺省时代码路径不变，用 sha256 证明基础世界与既有场景逐字节不变。
3. **承诺吸收来自真实账单结构。** 被 Savings Plan 覆盖的实例，每天两行（按需价与负的按需价）Unblended 相抵为 0，承诺费固定。停机少了覆盖用量，账单不动，承诺的未用部分同额变大。核实器靠 Amortized 与 Unblended 之差检出，并用承诺行的摊销增量独立印证。
4. **C01 是 claim，不是 agent 的 finding。** `--no-judge` 的确定性检测器里没有排期类 finding，判断层对 GT05 的结论是「不要停」。要核实「照按需价纸面值去停」会怎样，只能由场景声明这个纸面值：`on_demand_idle_hours`，按世界价格表算（按需小时价 x 24 x 30 x 闲置比例），不看账单。它进入 P0 的 findings 与 P1 的 `claims_resolved`，不进 agent 的 diff，表里标来源 claim，组合视图单列「仅 agent」。
5. **对照组分层多一维：类别 x 是否浪费类。** 无人使用的卷成本是平的，数据卷会增长。同层会让增长被错误套到被删的闲置卷上。细层（`ebs_volume:waste`、`ebs_volume:active`）没有对照资源时退回粗类别，再退回全体，所以原链数字不变（B 部分重新生成，与 c0018 相同）。
6. **分类按因，主因按优先级：承诺吸收 > 用量漂移 > 预测口径差 > 按天折算。** 口径差在扣除吸收与增长后计算：`gap = 实现 - 预测 x (反事实 / N 期成本)`；承诺吸收时用摊销口径节省。牌价口径差若有 N+1 期新增的用量类型（IOPS、吞吐），与短缺对账。
7. **首月现金实现率与次月现金实现率。** 标准月稳态实现率回答「是否兑现」，首月现金实现率回答「月报上看到多少」，次月（N+2）再测一次回答「是否拿满」。期中删除的 67.7% = 21/31 就是这样得到的。
8. **list_price 预测也带 N 期天数。** agent 的牌价估算是 14 天账单外推 x 天数 x 20%，在 31 天月份里偏大 31/30。c0018 的 9 月 30 天看不出，新链的 10 月 vol-0vfyd 预测 $62.00 暴露了它，换算标准月 $60.00。
9. **设计值对账。** 不看账单，只用世界规格与价格表算出每个偏差项应有的节省（首月现金 = 日均 x 未计费天数；摊销节省 = 按需价 x SP 折扣后 x 停机比例；校正后实现 = 规格增速下的反事实 - N+1 成本；等等），与核实器给出的数对账，1 美分内。这是「为什么对」的证据，不依赖「预测和账单对得上」。
10. **账单分解加「前期结转」项。** 上一期期中删除的资源，这一期尾巴归零。它是上期首月现金与标准月之差的补齐，不是「其他移除」。分解仍精确闭合（Fraction）。

## 范围之外

- `slo.py` 的 `diff_state` 语义（resolved 与「未再检出」的区分）归 t20。本链的每个 resolved 都是资源真的变了，不依赖这个区分；若 diff_state 改了语义，本链不受影响。
- 判断层与 `validate.py`（t19）、可视化（t14、t17）。
- 对真实账号的验证：数据仍是合成的，设计值对账证明核实器能还原世界里已知的因果，不证明真实账单的行为。
